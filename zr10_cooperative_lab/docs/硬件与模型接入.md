# 硬件与模型接入

本平台的仿真、单元测试和算法接口可直接在没有设备的电脑上运行。实机模式使用用户指定的 `siyi-sdk-v2` 接口，四台设备默认是 `192.168.144.25`～`192.168.144.28`，控制端口为 UDP `37260`。本次开发没有连接、扫描或转动真实设备；固件兼容性、方向符号、焦距内参及实际吞吐量需在实验台完成验收。

## 1. 网络与首次接入

四台 ZR10 分别接入交换机，电脑也接入同一交换机。电脑有线网卡设置成相同网段且不与设备冲突的地址，例如 `192.168.144.100/24`；已有实验网络有统一规划时按其规划填写。设备地址必须真实地分别配置为 `.25`～`.28`，不能只改 YAML 而让四台相机仍然使用相同的出厂地址。电脑同时连接 Wi-Fi 时，确认到 `192.168.144.0/24` 的路由走实验网卡。

先执行 README 中的只读 `probe` 命令。它并行读取固件和姿态，只会发送查询请求；不会切换模式或转动。UDP 没有 TCP 式握手，`connect_udp()` 返回并不代表设备在线，因此要看查询结果。确认 Windows 防火墙允许该 Python 环境接收实验网卡的 UDP 返回数据。

ZR10 是旧一代视频地址，默认配置为：

```text
rtsp://192.168.144.25:8554/main.264
rtsp://192.168.144.26:8554/main.264
rtsp://192.168.144.27:8554/main.264
rtsp://192.168.144.28:8554/main.264
```

有固件差异时，在每台设备的 `rtsp_url` 覆盖完整地址。`video1` 是 SDK 文档中新一代设备的路径，不能直接套到 ZR10。视频和 UDP 控制各自独立；能看到视频不表示控制连接正常，反之亦然。[SDK 视频文档](https://github.com/mzahana/siyi_sdk/blob/siyi-sdk-v2/docs/streaming.md)

逐台完成小角度动作验证后再运行四台协同实验。先设置较小速度限值和充分的机械余量，核对真实视轴朝向、回传角度以及坐标标定。软件急停只有在电脑能够向设备发送数据时才有效；拔掉网线无法保证停机报文到达，实验台应能直接切断云台电源。

## 2. 控制角度、速度与安装方向

`Action.yaw_deg/pitch_deg` 是每台设备经过标定后的本地 A/E 角。设备世界坐标与完整安装旋转由几何模块处理，不能把四台设备相同的原始 yaw 当成世界中相同方向。

```yaml
control:
  mode: velocity_p             # 也可用 position
  yaw_sign: 1                 # 原始角 = 本地角 * sign + offset
  pitch_sign: 1
  yaw_offset_deg: 0.0
  pitch_offset_deg: 0.0
  yaw_velocity_sign: 1         # 速度命令对“原始回传角”的方向，独立标定
  pitch_velocity_sign: -1
  normalize_pitch_feedback: true
  yaw_kp: 2.0
  pitch_kp: 2.0
  yaw_speed_limit: 25
  pitch_speed_limit: 25
  minimum_speed: 5
  deadband_deg: 0.5
  rate_hz: 10
  command_timeout_s: 0.25
  use_ack: true
  startup_lock: true
```

上面符号是示例，需要对各设备分别实测。`normalize_pitch_feedback` 用于部分旧固件俯仰回传相差 180° 的现象；原始值始终保存在 `Telemetry.raw.pitch_deg` 中。未发现该现象的固件可以关闭这个兼容开关。

SDK 的 `rotate(yaw, pitch)` 发送的是 **-100～100 的有符号整数速度等级**，不是度数，也不是 deg/s。`velocity_p` 根据目标角减实际角的误差生成这种速度等级；达到死区后发送零速。将速度等级 20 解释为 20°/s 会产生错误的运动模型。实际转速、最小可动速度、不同焦距下的抖动，应从 CSV 的指令与角速度回传中识别。设备配置中的机械角限位与姿态可达域同样需要实测。

`position` 使用 `set_attitude(yaw_deg, pitch_deg)` 发送绝对角目标。其 ACK 返回的是设备接收命令时的姿态，**不代表已到位**。本平台保留这份回执用于诊断，但不会用它刷新姿态遥测。必须用后续的独立姿态流判断实际运动。[SDK 云台编码实现](https://github.com/mzahana/siyi_sdk/blob/siyi-sdk-v2/siyi_sdk/commands/gimbal.py)、[SDK 客户端实现](https://github.com/mzahana/siyi_sdk/blob/siyi-sdk-v2/siyi_sdk/client.py)

## 3. 并行、租约、故障与停机

`HardwareFleet.start()` 创建每台设备各自的连接监督、姿态采集、控制、看门狗任务。`submit()` 只替换每台设备最新动作邮箱，不等待网络 ACK。用户算法应持续提供新动作；晚返回的旧动作不能覆盖时间戳更新的动作。

每个动作使用同一主机的 `time.monotonic()` 作为 `issued_t`，在 `issued_t + ttl_s` 到期。看门狗每约 10 ms 检查动作和遥测；如果正在等待 ACK 的动作过期，它先取消该动作协程，释放运动锁，再发送零速。因此一个慢 ACK 不会让看门狗一直等在同一把锁后。所有 SDK 请求还有单独超时，故障设备的任务不会阻塞其他设备。操作系统、Python 调度和驱动决定实际响应时间，本平台没有声称硬实时保证。

程序退出或连接失败时，先取消控制任务，再重复 `rotate(0,0)`。ACK 失败时补发 `rotate_nowait(0,0)`，并在事件中记录停机是否被确认。正在进行的手动对焦和手动变焦也会发送 0。它们有独立租约：随后只下发角度动作，不会给之前的镜头运动无限续租。

姿态推流请求失败时自动退回轮询；姿态持续过期则重新创建 UDP 会话。重连清除旧动作和旧姿态历史，要求算法重新产生动作。建立实机连接时会先停止运动，默认发送 LOCK 模式命令；不自动归中，避免归中路径穿过意外方向。LOCK 属于发送后不等 ACK 的操作，不能仅凭发送成功就认为模式已确认。

常用系统项：

```yaml
system:
  rate_hz: 10
  attitude_stream_hz: 10       # 2、4、5、10、20、50、100
  telemetry_stale_s: 0.5
  fallback_poll_interval_s: 0.2
  reconnect_stale_s: 2.0
  reconnect_initial_s: 0.5
  max_command_errors: 3
  telemetry_history_size: 1000
  stop_repetitions: 2
  zoom_poll_s: 1.0
  max_frame_age_s: 0.6
```

ACK 失败不会自动重发非零速度，也不会重试拍照、录像切换、HDR 切换。报文已到设备但 ACK 丢失时，设备可能已执行，因此这些操作的失败含义是“未确认”，不能视为“肯定没有发生”。

## 4. 镜头及其他参数

动作参数必须同时满足三件事：已在 `actions.PARAMETERS` 注册、在 `action_space.enabled` 中启用、设备 `capabilities` 已确认支持。默认只启用角度适合最初的协同算法。非法字段会在发送任何指令前被拒绝，参数名不会直接映射到任意 SDK 方法。

| 字段 | 内容 | 硬件语义 |
|---|---|---|
| `Action.zoom` | 绝对倍率 | `absolute_zoom()`；不把指令值冒充实际反馈 |
| `parameters.focal_length_mm` | 毫米 | 统一校验器按实测焦距表换成倍率，再交给硬件 |
| `focus_direction` | -1/0/+1 | 手动对焦协议方向；0 停止 |
| `zoom_direction` | -1/0/+1 | 缩小/停止/放大，需要新鲜倍率反馈执行限位 |
| `autofocus` | true | 在配置图像中心触发一次对焦 |
| `gimbal_mode` | lock/follow/fpv | 云台模式切换，发送未确认 |
| `photo` | true | 拍照触发，发送未确认 |
| `record_toggle` | true | 发送 SDK START_RECORD，示例固件再次发送切换停止 |
| `hdr_toggle` | true | 固件可选 HDR 操作；协议列有不支持提示，默认不要启用 |
| `osd` | true/false | OSD 开关 |
| `encoding` | 字典 | 视频编码参数，需固件验证 |

上游协议与对焦示例把 `-1` 写为近、`+1` 写为远，而客户端某处注释反过来；因此代码只保存原始协议方向，实验前应验证近远。`photo/record_toggle/hdr_toggle` 是触发事件：相同 `issued_t` 只执行一次；如果每个周期都给新的 `issued_t` 且保持 true，就会反复触发。请在算法中只在状态变化时发一次此类动作。[SDK 对焦示例](https://github.com/mzahana/siyi_sdk/blob/siyi-sdk-v2/examples/focus_control.py)、[SDK 录像示例](https://github.com/mzahana/siyi_sdk/blob/siyi-sdk-v2/examples/camera_capture.py)

`encoding` 明确要求 `width`、`height`、`bitrate_kbps` 三个正整数字段；可选 `stream: MAIN/SUB/RECORDING` 和 `codec: H264/H265`。当前 SDK 编码器仅接受 1920×1080 或 1280×720，虽然模型中有 `frame_rate` 字段，但写入报文没有携带它，所以本平台明确拒绝 `fps` 参数，不会假称已改变帧率。没有“根据键名猜测”的兼容层。修改分辨率、裁切、变焦或电子防抖可能改变内参，修改编码也可能改变延迟，必须重新检查标定。本平台不承诺 ZR10 每个固件都支持通用 SIYI SDK 的全部可选命令。

滚转读数保留用于像素射线变换；当前 SDK 未提供 ZR10 独立滚转动作。光圈、曝光、白平衡、增益等在动作目录中明确标记支持状态，未核实的写接口不伪装成可执行参数。未来取得厂商新协议后可在注册表、校验器和硬件适配器三处加一个参数；算法输入/输出边界不变。

## 5. 使用已有 YOLO 模型

可先使用只读四路预览检查视频和识别效果，它不连接 UDP 控制通道：

```powershell
python -m zr10lab.viewer --config configs/four_zr10.yaml
python -m zr10lab.viewer --config configs/four_zr10.yaml --detect
```

预览需要带桌面支持的 `opencv-python`。如果此前安装的是 `opencv-python-headless`，请按 README 中可选依赖说明切换，不要同时安装两个提供同一个 `cv2` 模块的包。界面按 Q / Esc 退出；无视频时显示占位，检测在后台执行，检测框和显示图像来自同一帧。窗口中的 `--fps` 只限制界面刷新率，不改变设备编码帧率。

将自己的训练权重放入 `models`，相对路径按 YAML 所在目录解析：

```yaml
detector:
  type: ultralytics
  model_path: ../models/drone.pt
  confidence: 0.35
  iou: 0.5
  image_size: 640
  device: cpu                 # GPU 环境验证后可设置为 0
  classes: [0]                # 必须改成自己模型中的无人机类别编号
```

安装可选依赖 `ultralytics` 后即可使用它支持的 YOLO 检测权重。兼容 `type: yolo`、`weights`、`imgsz` 别名；如果别名和正式字段同时提供不同值会报错。权重不存在时会报出具体路径，不会悄悄下载通用模型替代。YOLO 检测结果框恢复到原始视频像素坐标；标签序号来自训练模型，不能假定所有模型都把无人机编为 0。

每路视频由独立进程解码，进程间队列容量为 1，推理来不及会覆盖旧帧。单个后台推理线程轮流处理四台相机的最新帧，共享一个模型实例，避免多线程同时进入同一个模型引起状态竞争，也减少显存重复占用。控制线程不运行 OpenCV 解码和模型推理。慢推理结果在完成后再次检查年龄，过期就丢弃。每个帧 ID 只消费一次，不能把上一帧的框重复当作新观测。

这套默认实现便于调试。四路高分辨率视频的解码、进程间图像拷贝及串行模型推理可能成为瓶颈；用日志中的实际 `inference_ms/age_ms/skipped_frames` 决定是否需要 TensorRT、共享内存或 GPU batch 推理。优化这些部分时保留 `Detection` 输出契约即可。

## 6. 轻量化 ONNX 与自定义模型

内置 ONNX 用 OpenCV DNN，只接受明确的单输入、单输出、batch=1 合约：

```yaml
detector:
  type: onnx
  model_path: ../models/drone.onnx
  output_format: yolov8       # 必须显式填写
  input_size: [640, 640]      # 宽、高
  confidence: 0.35
  iou: 0.5
  classes: [0]
  labels: [drone]
```

输入处理为 BGR→RGB、缩放为 0～1、NCHW、114 灰色 letterbox。`yolov8` 输出形状为 `(1,4+C,N)` 或 `(4+C,N)`，包含输入图坐标的中心 xywh 和 C 个类别概率，不含 objectness。`xyxy_score_class` 输出形状为 `(1,N,6)` 或 `(N,6)`，列为输入图像素单位的 x1,y1,x2,y2,概率,类别整数。两者均做按类别 NMS，然后减去 letterbox 偏移、除缩放率，恢复原图坐标。

YOLOv5 的 objectness 输出、归一化坐标、多输出模型、量化输入、其他 RGB/BGR 或归一化规则，请用 custom 插件准确实现，不能仅靠换一个 `output_format` 名字就当兼容。示例：

```python
# my_detector.py 放在项目根目录或可导入的 Python 包中。
from zr10lab.vision import PixelDetection

class MyDetector:
    def __init__(self, config):
        # 在这里加载自己的 ONNX Runtime / TensorRT / PyTorch 模型。
        self.config = config

    def detect(self, image_bgr):
        # 真实实现应调用自己的模型，并把输出还原到 image_bgr 原始像素坐标。
        # 没有检测到目标时返回 []。以下空结果仅用于说明接口，不是假识别器。
        return []

def create_detector(config):
    return MyDetector(config)
```

```yaml
detector:
  type: custom
  factory: my_detector:create_detector
  model_path: ../models/my_model.onnx
```

每个结果可以是 `PixelDetection` 或同字段字典。必要字段为 `bbox_xyxy` 和 `confidence`，可带 `class_id`、`label`、`local_track_id`、`embedding`。框必须具有正面积和有限数值；非法模型输出会作为视觉错误记录。`local_track_id` 仅代表单相机身份，不能拿它直接当多站同一目标的全局身份。跨站关联仍由融合模块完成。

## 7. 帧与姿态的时间标定

SDK 的普通姿态推流、OpenCV RTSP 解码不提供已验证的统一曝光时刻。本平台采用：

```text
估计曝光时刻 = 主机解码收到帧的 monotonic 时刻 - video_latency_s
```

每台相机可配置：

```yaml
camera:
  video_latency_s: 0.0        # 默认未知偏差；测得后填写，不要照抄宣传延迟
  time_uncertainty_s: 0.15    # 包括未补偿的编码、传输、排队抖动等
  open_timeout_ms: 3000
  read_timeout_ms: 1000
  reconnect_s: 1.0
```

帧事件中的 `timestamp_kind=host_receive_estimate` 明确标识来源，保存接收时刻、估计时刻、推理耗时和年龄。可以用闪灯/屏幕时码及可见云台运动实验估计固定延迟和抖动，再对齐姿态历史。仅把四台主机接收时间排序，不会获得真正硬件同步。

运动目标应在配置的时间差门限内融合，并将时间不确定性加入定位误差估计。目标速度越快、云台转得越快，错误时间配对越容易产生很大的位置偏差。滤波器平滑不能消除这种系统误差；先校正时间，再评估轨迹。

倍率查询结果记录 `zoom_known/zoom_t`，超过 `system.zoom_stale_s`（默认 2 秒）后视为未知。`zoom_stable` 标记绝对变焦未到目标或连续变焦进行中的过渡状态，此时暂停使用该路像素进行定位。绝对变焦同样受动作租约约束。如果旧固件不支持查询，日志会说明，不能用最近发送的目标倍率替代实际倍率。固定倍率也需要明确验证；多倍率实验则应建立对应内参表，并避免使用变焦过渡期间未知内参的帧。

## 8. 日志与验收顺序

硬件适配器通过 `telemetry_sink(Telemetry)` 逐包输出接收到的姿态样本，运行器将其写入 `telemetry_stream.csv`。每个姿态包保留主机接收单调时刻、UTC 接收时刻、序号、stream/poll 来源、校准后角度及 `raw` 中未改写的 SDK 角度和角速度。`telemetry.csv` 另存决策周期快照：即使控制算法只以 10 Hz 运行，也不会因为快照采样而丢掉收到的 50 Hz 姿态数据。反复读取快照不会重复触发原始样本回调。这两张表分别用于重做标定/时间插值，以及还原算法在每个周期实际使用的状态。UDP 在到达主机之前丢失的数据无法由该机制恢复。

`event_sink(kind,payload)` 还输出连接/重连、变焦查询、停机确认、参数发送等事件；`result_sink(CommandResult)` 输出动作状态、耗时、实际下发 SDK 参数和错误。三个 sink 的异常均捕获并保存在 `last_sink_error`，不会阻止设备停机；运行器仍应通过记录器健康检查结束无法可靠记录的实验。CSV 统一写入器由运行器负责，避免每台设备线程自行抢写文件。`CommandResult.ack` 指角度/速度主命令回执；额外参数是否有回执见 `applied` 中各自的 `ack`。这里的 ACK 不表示机械到位。

建议按以下顺序验收：

1. 纯仿真跑完整闭环，检查轨迹、关联、CSV 和算法接口。
2. 四台只读查询，确认各 IP 唯一、姿态刷新、固件版本。
3. 每台单独小角度运动，验证正负方向、软限位和退出停机。
4. 故意停止算法输出、延迟模型推理，验证 TTL 和看门狗事件。
5. 接入真实 YOLO，检查图像框、类别、时刻、原始图像分辨率。
6. 固定已知靶点做各倍率内参、设备坐标及安装姿态标定。
7. 静态目标两站定位，再增加到四站与多目标，最后验证运动轨迹。
8. 统计定位误差、失锁时间、推理和控制延迟，逐项决定优化目标。

单元测试只使用假 SDK 和确定性数组，覆盖通信语义、独立看门狗、过期命令拒绝、旧动作覆盖保护、ACK 丢失停机、像素解码、帧去重及迟到结果丢弃。它们证明软件边界的行为，不能替代上述固件和实验几何验收。
