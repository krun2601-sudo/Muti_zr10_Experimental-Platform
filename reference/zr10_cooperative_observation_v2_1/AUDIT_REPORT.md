# v1.3 全面审计与 v2.0 修复说明

## 审计依据

审计了用户上传项目中的源码、YAML 配置和 2026-07-27 产生的多次实验日志。

## 日志中确认的故障

### 1. 连接阶段存在并发突发

部分会话中三台设备的 `get_firmware_version()` 同时超时；另一次仅 `.25` 和 `.27` 成功、`.26` 超时。v1.3 使用 `asyncio.gather()` 同时建立三条连接并立即查询固件、清理流和订阅反馈，容易形成启动突发。

**修复：** v2.0 默认逐台连接，连接间隔 0.25 s，每台独立重试三次。

### 2. 三台设备均连接，但完全无法到达初始 AE

多个会话中三台设备都成功查询固件，随后每台连续三次、每次 12 s 无法到达 `(0°, -10°)`。日志没有记录任何运动命令异常。

源码显示 v1.3 的速度控制和停止均使用 `rotate_nowait()`。该调用不等待 ACK，因此“Python 调用成功”只表示 UDP 数据已交给操作系统，不能证明旧款 ZR10 已接收或执行。

**修复：** v2.0 默认使用 `rotate()`，要求设备 ACK；ACK 超时后才使用 `rotate_nowait()` 降级，并将降级写入 CSV 和事件日志。

### 3. 初始化是全有或全无，缺少运动过程诊断

v1.3 只在 12 s 超时后给出“未到达”，没有显示实际角度、误差、速度命令和命令状态。

**修复：** 初始化期间每秒打印目标 AE、实际 AE、误差、速度和 ACK 状态。

### 4. 启动模式设置可能不兼容旧固件

`capture(LOCK_MODE)` 在 v1.3 中属于强制步骤，任何异常都会导致初始化失败。

**修复：** 默认改为 best-effort；只有 `startup_lock_required: true` 时才作为致命错误。

### 5. 旧包导入污染

从 `tools/recover_devices.py` 启动时，Python 曾导入旧目录的 `zr10_coop`。这是因为工具脚本目录位于 `sys.path[0]`，项目根目录不一定优先。

**修复：** 所有工具脚本显式将当前项目根目录插入 `sys.path[0]`；主程序打印版本和实际包路径。

### 6. 反馈过期时仍可能继续控制

v1.3 的速度 P 控制可使用缓存中的旧反馈计算命令。

**修复：** 反馈超过 `feedback_stale_s` 时先发送停止命令并返回错误，不再使用旧姿态控制。

### 7. 轮询异常被静默丢弃

管理器对 `poll_feedback()` 使用 `return_exceptions=True`，但没有记录结果。

**修复：** 轮询异常写入事件日志。

### 8. 策略阶段切换未强制发送

若内部状态或重发条件异常，新阶段第一条目标可能不立即发出。

**修复：** 首周期和策略 phase 变化时强制发送。

### 9. 关闭阶段停止命令不可确认

v1.3 退出时只发送 `rotate_nowait(0, 0)`。

**修复：** v2.0 发送带 ACK 的停止命令，失败时降级，并按配置重复发送。

## 仍需要真实硬件确认的事项

软件测试无法替代以下硬件标定：

1. 每台设备正 yaw、负 pitch 的实际方向；
2. 各台安装零偏；
3. 不同固件对 LOCK 模式和姿态推流的支持；
4. 三路视频与三路控制同时运行时的交换机带宽和主机解码负载。

请先运行 `tools/hardware_diagnose.py`，再运行主程序。
